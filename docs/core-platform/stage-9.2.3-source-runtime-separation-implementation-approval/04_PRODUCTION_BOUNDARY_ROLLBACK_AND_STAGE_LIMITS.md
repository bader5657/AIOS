# Production Boundary, Rollback, and Stage Limits

## Production boundary

`VPS / PRODUCTION EXECUTION = PROHIBITED`

This implementation approval does not authorize creation of the runtime cache,
permission changes, installed-unit preservation or replacement, service stop
or start, daemon reload, source-residue disposition, Telegram activity,
PostgreSQL/Storage access, or reboot.

After repository implementation and its separate verification/closure, a
future controlled VPS approval may authorize only:

1. create `/opt/aios/runtime/cache/pycache`;
2. set `aiosadmin:aiosadmin` and mode `0750`;
3. preserve the installed Stage 9.2.2 unit as rollback evidence;
4. stop the service once and prove the zero-poller gate;
5. quarantine or remove only exactly enumerated generated bytecode residue;
6. install the corrected approved unit and run `daemon-reload`;
7. start once and prove exactly one poller;
8. exercise normal imports/runtime activity;
9. prove `/opt/aios-src` remains completely clean; and
10. prove `.pyc` appears only below the approved runtime cache.

No reboot is required. Stage 9.2.2 already proved reboot activation.

## Future rollback

If the corrected service fails, future controlled rollback is:

1. stop the corrected service;
2. restore the prior Stage 9.2.2 installed unit;
3. run `daemon-reload`;
4. start once; and
5. prove exactly one polling process.

The disposable runtime cache may remain. No source, runtime configuration,
venv, database/schema, Docker, Storage, or business-data rollback is required
or authorized.

## Existing generated residue

Existing source bytecode remains classified:

`KNOWN GENERATED SOURCE-TREE RUNTIME RESIDUE — NON-BLOCKING FOR STAGE 9.2.2`

Its exact future quarantine/removal procedure requires separate production
authority. Broad wildcard deletion is prohibited.

## Later-stage boundaries

Stage 9.2.4 retains the complete secrets, database-data, logs, backups, and
original-business-file Git exclusion audit. Stage 9.3.1 retains README,
