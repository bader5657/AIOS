# Stage 3.4.1 Verification, Acceptance, and Rollback

## Verification Gates for Future Implementation

All gates are mandatory:

1. **Scope gate:** diff contains only separately approved files from
   `04_FUTURE_IMPLEMENTATION_SCOPE.md`; prohibited stages and authorities are
   unchanged.
2. **Schema gate:** `config/ingestion-manifest.schema.json` parses as valid JSON
   Schema, has `$schema`, root object/type, `properties`, `required`, and
   `additionalProperties: false`.
3. **Contract gate:** universal and conditional requiredness, non-null/non-empty
   values, omission rules, status constant, and unknown-field rejection are
   proven.
4. **Applicability gate:** Text, Image, Voice, Audio, Video, PDF, DOC/DOCX,
   Spreadsheet, Web Link, and YouTube Link each produce the correct relationship
   shape after successful Metadata.
5. **Identity gate:** `manifest_id` is unique and opaque; tests infer no business
   meaning from its format.
6. **Metadata gate:** the exact validated Stage 3.3 bounded result is passed;
   no re-extraction, mutation, or new metadata field occurs.
7. **Original gate:** file size and SHA-256 are proven against exact stored
   original bytes; manifest creation neither embeds nor changes those bytes.
8. **URL gate:** exact URL preservation is proven and source/code inspection
   confirms no fetch, download, dereference, enrichment, or snapshot behavior.
9. **Time gate:** timestamps accepted or generated by their defined boundary are
   UTC RFC 3339; absent timezone is rejected rather than guessed.
10. **Serialization gate:** UTF-8 JSON runtime output validates against the
    normative schema and round-trips with approved primitives and meaning.
11. **Lifecycle/failure gate:** Store Original → Extract Metadata → Create
    Manifest ordering passes; Metadata or Manifest failure prevents Register
    readiness/execution; partial output is removed or unmistakably invalid.
12. **Boundary gate:** Registry is not implemented, no dependency is added, and
    the existing Manifest storage root is reused.
13. **Regression gate:** focused Document Manifest, universal-ingestion,
    lifecycle-boundary, capability-matrix, and relevant storage-path tests pass,
    followed by the repository's established Core Platform regression command.

## Implementation Acceptance Criteria

Implementation may be accepted only when every gate passes on an exact recorded
commit, the runtime/schema diff has no unexplained behavior, current drift rows
in the conformance matrix are resolved or explicitly re-approved, and review
finds no semantic divergence between `Manifest` and `Document Manifest`.

Authority activation alone is not implementation acceptance. A separate scoped
implementation approval must precede edits, and separate review/acceptance
evidence must follow them.

## Rollback Condition

Rollback is mandatory if an accepted implementation is found to violate any
required field or conditional rule, accept unknown fields, serialize invalid
schema output, change metadata meaning, hash anything other than exact stored
original bytes, guess time/source values, perform network retrieval, treat
Manifest as a media type, execute Register after Manifest failure, leave a
failed artifact valid-looking, modify an unapproved file, or cross any
prohibited-stage boundary.

Rollback means reverting the Stage 3.4.1 implementation commit(s) to the last
known conforming runtime baseline while retaining this active authority package
as the contract to satisfy. Any authority change instead requires a new Project
Owner decision; runtime drift cannot amend authority.
